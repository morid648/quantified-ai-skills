# Annotation Guideline Writer

Creates comprehensive, unambiguous annotation instructions and labeling schemas for human annotators or automated tagging pipelines. Enforces edge-case protocols and evaluates instruction quality against a quantified completeness checklist.

## When to Use

Use this skill when you need to:
- Establish formal labeling guidelines before launching an annotation campaign.
- Define explicit taxonomy boundaries, entity schemas, and normalization rules.
- Systematically document edge cases, ambiguous boundaries, and conflict resolution policies.
- Audit existing annotation instructions for gaps, ambiguity, or missing worked examples.

Do NOT use this skill for:
- Computing statistical agreement between annotators (use `annotation-qa-scoring`).
- Executing domain tagging directly on financial documents (use `finance-document-annotator`).

## Core Components of an Annotation Guideline

Every complete guideline generated by this skill must incorporate five foundational components:

1. **Task Objective & Target Domain**: High-level purpose of the annotation effort and downstream model use case.
2. **Entity Taxonomy & Schema Specification**: Strict definitions for every field or tag, data types, whether optional or required, and valid enumeration sets.
3. **Boundary & Normalization Rules**: Exact text span start/end criteria, handling of punctuation, whitespace, currency symbols, and date formatting (ISO-8601).
4. **Negative & Edge-Case Catalog**: Explicit rules for missing data, contradictory values, OCR errors, and ambiguous phrases.
5. **Annotated Reference Examples**: At least 3–5 representative examples containing both standard cases and difficult edge cases with explanatory annotations.

## Guideline Completeness Scoring

Guidelines are audited against a 10-point binary checklist ($C_1 \dots C_{10}$):

| Item ID | Verification Check | Weight (%) |
|---|---|---|
| $C_1$ | Explicit task scope and domain defined | 10 |
| $C_2$ | Complete taxonomy of entity classes / fields | 10 |
| $C_3$ | Data types and formatting requirements specified | 10 |
| $C_4$ | Span boundary selection criteria (e.g. whitespace, articles) | 10 |
| $C_5$ | Normalization rules for numeric/currency/date fields | 10 |
| $C_6$ | Null/missing field handling protocol | 10 |
| $C_7$ | Ambiguous/conflicting evidence resolution hierarchy | 10 |
| $C_8$ | Low-confidence / escalation flagging rules | 10 |
| $C_9$ | Minimum 3 worked positive/negative examples with rationale | 10 |
| $C_{10}$ | Explicit list of out-of-scope entities / non-targets | 10 |

$$\text{Guideline Completeness Score (\%)} = \left( \frac{\sum_{i=1}^{10} C_i}{10} \right) \times 100$$

## Examples

### Example: Invoice Line-Item Extraction Guideline Specification

```markdown
### Field: `line_items.unit_price`
- **Definition**: The individual price per single unit before quantity multiplication, tax, or discounts.
- **Type**: Float (normalized to 2 decimal places, stripped of currency symbols).
- **Boundary Rule**: Capture only the numeric token adjacent to the unit measure. Do NOT include currency symbols or quantity tokens.
- **Edge Case - Bulk Discounts**: If a line item displays "3 @ $10.00 (discounted to $8.00)", annotate `8.00` as effective unit price and flag `discount_applied: true`.
- **Negative Case**: Do not tag shipping freight line items as product line items; categorize under `shipping_fee`.
```

## Limitations

- **Does not recruit or monitor annotators**: Focuses solely on specification and quality grading of the guideline document itself.
- **Does not replace domain SME validation**: While structural completeness is measured, domain accuracy requires expert review.
- **Static evaluation**: Cannot dynamically predict all human misunderstanding without pilot annotation feedback.
